# قرارداد ذخیره‌سازی و حریم خصوصی — مرحله ۲

## جداسازی

identity.db فقط کاربران، مدیران، مجوزها، Audit مدیریت و وضعیت Bootstrap را دارد.
internal.db دارای داده بازخورد داخلی و external.db همان ساختار به‌همراه فهرست
افراد خارجی و درخواست معرفی فرد است. هر فایل شناسه حوزه و شناسه تصادفی نصب
دارد. تغییر نام فایل خارجی به داخلی در بررسی راه‌اندازی رد می‌شود.

این مرز فایل، دفاع در برابر خطای برنامه‌نویسی است؛ کاربری که فایل‌ها یا کد
سرور را در اختیار دارد می‌تواند SQL اجرا کند. مدیر برنامه چنین دسترسی‌ای ندارد.
مدل مجوز سرویس/Repository در مرحله ۳ ساخته می‌شود؛ زیرساخت مرحله ۲ به‌تنهایی
ادعای اجرای Permission Matrix را ندارد.

## Schema و تراکنش

Schema اولیه در `app/database/schema_v1.py` ثابت است و توسط revision شماره 0001
Alembic اجرا می‌شود. تغییر آتی باید revision جدید داشته باشد. Downgrade مخرب
عمداً رد می‌شود. ستون‌ها، PK، FK، UNIQUE، CHECK و Index در
[SQL کامل Schema](DATABASE_SCHEMA.md) ثبت شده‌اند.

شناسه رکوردها تصادفی است و توسط برنامه تولید می‌شود؛ برای SQL خام باید id
صریح داده شود. created_at و updated_at، ثانیه UTC هستند و پیش‌فرض دیتابیس دارند.
updated_at در به‌روزرسانی‌های SQLAlchemy خودکار تغییر می‌کند؛ SQL خام چنین
تضمینی ندارد. برای پیام‌ها اصل بر تغییرناپذیری محتواست.

هر اتصال foreign_keys=ON، journal_mode=WAL، synchronous=FULL، busy_timeout=5000
و secure_delete=ON دارد. BEGIN صریح باعث می‌شود DDL و شماره migration نیز همراه
خطا Rollback شوند. secure_delete تضمین حذف از Backup، WAL یا رسانه ذخیره‌سازی نیست.
صف تحویل و پیام در یک تراکنش یک دیتابیس ثبت می‌شوند. شکست و لغو coroutine
باعث Rollback می‌شود. هر فایل یک اتصال در Pool دارد؛ اجرای چند فرایند نویسنده
یا قرار دادن SQLite روی فایل‌سیستم شبکه‌ای توصیه نمی‌شود.

Migration هر فایل اتمی است؛ سه فایل تراکنش مشترک ندارند. اگر اجرای ارتقا بین
فایل‌ها قطع شود، اجرای دوباره آن را ادامه می‌دهد. برنامه فقط زمانی شروع می‌شود
که بررسی هر سه فایل موفق باشد. Migration خودکار هنگام اجرای ربات انجام نمی‌شود.
ارتقاهای بعدی باید پس از Backup هماهنگ و توقف نویسندگان اجرا شوند؛ ابزار Backup
در مرحله ۹ تحویل می‌شود.

## رمزگذاری

AES-256-GCM با nonce تصادفی ۱۲ بایتی برای هر بار رمزگذاری استفاده می‌شود.
هر حوزه سه کلید مستقل ۳۲ بایتی دارد: content، routing و index. کلید index
فقط برای HMAC-SHA256 است. AAD شامل نسخه قالب، نسخه کلید، حوزه، هدف رمزگذاری،
شناسه رکورد و نام فیلد است. تغییر ciphertext یا انتقالش به رکورد/فیلد/حوزه
دیگر خطای احراز اصالت می‌دهد. جهت پیام نیز در direction_cipher رمزگذاری می‌شود.

قالب ciphertext دارای magic، نسخه کلید، nonce و خروجی AEAD است؛ متن یا شناسه
نویسنده در header وجود ندارد. فایل keyring نسخه‌دار است. ایجاد اولیه انحصاری
است؛ فایل موجود بازنویسی نمی‌شود. کلیدهای تکراری در حوزه‌ها/کاربردها رد می‌شوند.
Probe رمزگذاری‌شده و HMAC در هر دیتابیس حوزه، جایگزینی اشتباه هر یک از سه
کلید را تشخیص می‌دهد. کلیدها داخل دیتابیس نیستند.

خواندن ciphertext نسخه‌های نگهداری‌شده پشتیبانی می‌شود، اما ابزار گردش عملیاتی
کلید و بازسازی Index هنوز ارائه نشده است. مقدار active یا محتویات keyring را
دستی تغییر ندهید؛ برنامه نسخه فعال بدون binding معتبر را رد می‌کند. برنامه
هرگز در نبود کلید، خودکار کلید جدید تولید نمی‌کند.

HMAC شرکت‌کننده باید با namespace اختصاصی و اجزای conversation_id و user_id
فراخوانی شود. HMAC هفتگی باید دوره و حوزه داشته باشد. جداسازی اجزا با JSON
از برخورد ناشی از چسباندن ساده رشته‌ها جلوگیری می‌کند. برچسب‌ها متن پیام یا
شناسه حساب نیستند، اما صرف استفاده از HMAC ناشناس‌بودن مطلق ایجاد نمی‌کند.

## محدودیت‌ها

رمزگذاری در سطح فیلد است، نه رمزگذاری کل فایل SQLite. کاربران، نام افراد خارجی،
نوع و زمان رکوردها، شمار رکوردها و روابط داخلی بین پیام/مکالمه در فایل قابل
مشاهده‌اند. ستون sender_id روشن در دیتابیس حوزه نداریم؛ بدنه و مسیر و جهت
حساس باید فقط از API رمزگذاری عبور کنند. نوع BLOB به‌تنهایی صحت رمزگذاری را
تضمین نمی‌کند؛ سرویس‌های مراحل بعد مسئول رعایت این قرارداد خواهند بود.

فایل کلید خارج از DATA_DIR است، ولی به‌صورت پیش‌فرض روی همان میزبان قرار دارد؛
این کار در برابر root یا Backup کامل میزبان محافظت ایجاد نمی‌کند. برای استقرار
نهایی باید Secrets mount یا فضای حفاظت‌شده مستقل و نسخه پشتیبان کلید جداگانه
داشت. گم‌شدن کلید اصلی یعنی از دست رفتن امکان بازیابی داده رمزگذاری‌شده.

db-check طرح جدول‌ها/ستون‌ها، نسخه، هویت حوزه، Probe کلیدها، quick_check و
foreign_key_check را بررسی می‌کند؛ این دستور رمزگشایی تک‌تک پیام‌های ذخیره‌شده
یا تضمین سلامت سخت‌افزار نیست. خطاها به خروجی عمومی و فاقد داده حساس تبدیل می‌شوند.
