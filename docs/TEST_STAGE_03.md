# تست مرحله سوم: کاربران و مجوزها

راهنمای تاریخی مرحله ۳: در نسخه مرحله ۴، تایپ شناسه برای افزودن کاربر/مدیر با
[انتخاب‌گر Telegram](TEST_STAGE_04.md) جایگزین شده است.

## نتیجه بررسی توسعه‌دهنده

- ۱۰۸ تست خودکار پس از آخرین تغییرات پاس شد.
- Ruff و بررسی قالب هر ۳۹ فایل Python پاس شدند.
- مدیر اولیه از تنظیمات موجود ثبت شد؛ اجرای مجدد Bootstrap مجوزها را تغییر نداد.
- db-check واقعی برای هر سه دیتابیس موفق بود؛ Schema همان 0001 باقی مانده است.
- توکن، `.env` و کلیدهای رمزگذاری تغییر نکردند.
- تست تعاملی Telegram پس از Restart بر عهده کاربر است؛ مرحله ۴ شروع نشده است.

## راه‌اندازی

فرایند قبلی ربات را با Ctrl+C متوقف کنید و از پوشه پروژه اجرا کنید:

```powershell
uv sync --locked
uv run --locked python -m app.cli db-check
uv run --locked python -m app.cli admin-bootstrap
uv run --locked python -m app.main
```

نیازی به تغییر `.env`، ساخت کلید تازه یا حذف دیتابیس نیست. Schema همچنان 0001
است. Bootstrap در اولین اجرای ربات نیز خودکار انجام می‌شود؛ فرمان جدا فقط
برای راه‌اندازی و صحت‌سنجی بدون اتصال Telegram است. اگر قبلاً انجام شده، پیام
عدم تغییر مجوزها صحیح است. نام حساب‌های اولیه «مدیر اولیه ۱» و مانند آن است؛
از بخش کاربران می‌توانید نام را اصلاح کنید. نام یا username تلگرام خودکار ذخیره نمی‌شود.

## تست در Telegram

۱. با حساب مدیر `/start` بفرستید. پیام مرحله ۳، پروفایل، راهنما و پنل مدیریت
باید دیده شوند. `/admin` هم پنل مدیریت را باز می‌کند.

۲. پنل مدیریت ← کاربران ← افزودن کاربر: ابتدا شناسه عددی یک حساب آزمایشی،
سپس نام نمایشی را بفرستید. پیش‌نمایش نام و شناسه را بررسی و تأیید کنید.
تکرار همان شناسه باید خطای قابل فهم بدهد. ثبت کاربر به او پیام خودکار نمی‌فرستد؛
او باید ربات را در گفتگوی خصوصی Start کند.

۳. با حساب تازه `/start` بفرستید. باید وارد شود ولی دکمه مدیریت نداشته باشد.
`/admin` از همین حساب باید رد شود. پروفایل فقط نام همین کاربر را نشان دهد؛
آمار در مرحله ۶ اضافه می‌شود.

۴. از فهرست کاربران، حساب آزمایشی را غیرفعال و تأیید کنید. `/start` و دکمه‌های
قدیمی برای او باید رد شوند. دوباره فعال کنید؛ دسترسی عادی باید برگردد.
«حذف نرم» همان غیرفعال‌سازی است و رکورد از دیتابیس حذف نمی‌شود.

۵. اصلاح نام، جستجو با بخشی از نام و شناسه عددی را امتحان کنید. با بیش از
۱۰ کاربر، صفحه‌بندی ظاهر می‌شود. جستجوی `%` نباید کل فهرست را برگرداند.

۶. مدیران ← افزودن / تغییر نقش مدیر: شناسه همان کاربر فعال را بدهید، «مدیر
خارجی» را انتخاب و تأیید کنید. پنل آن حساب فقط حوزه خارجی را نشان می‌دهد و
دکمه کاربران یا مدیران ندارد. مدیریت افراد خارجی در مرحله ۵ فعال می‌شود.
مدیر داخلی می‌تواند کاربران عادی را مدیریت کند، ولی اختیار تغییر مدیران ندارد.

۷. با مدیر اولیه، نقش حساب آزمایشی را به مدیر کامل تغییر دهید. بدون انتخاب
گزینه «مدیریت مدیران»، مدیر کامل هم نباید بتواند مدیران را مدیریت کند.
این اختیار فقط با گزینه صریح «مدیر کامل + مدیریت مدیران» واگذار می‌شود.

۸. از فهرست مدیران، مدیریت حساب آزمایشی را لغو کنید. باید به کاربر عادی
تبدیل شود. Restart ربات نباید مجوز لغوشده را برگرداند؛ تنظیمات اولیه فقط بار
اول مصرف می‌شوند. برای این تست شناسه‌ها را در `.env` تغییر ندهید.

۹. لغو مدیریت یا غیرفعال‌کردن آخرین مسئول فعال مدیریت مدیران باید رد شود.
این رفتار محافظتی است؛ برای تست انتقال اختیار ابتدا مدیر مسئول دوم ثبت کنید.

۱۰. قبل از تأیید افزودن کاربر، لغو یا `/cancel` را بزنید. دکمه تأیید قدیمی
باید نامعتبر شود. دکمه‌ها یک‌بارمصرف و به همان حساب وابسته‌اند؛ پس از ۱۰ دقیقه
یا Restart باید از `/start` شروع کنید. هر کلیک، دکمه‌های مرحله قبلی را منقضی می‌کند.

## تست‌های خودکار

```powershell
uv run --locked pytest -q
uv run --locked ruff check .
uv run --locked ruff format --check .
```

این تست‌ها از دیتابیس موقت و Telegram شبیه‌سازی‌شده استفاده می‌کنند؛ حساب‌های
واقعی شما اضافه، غیرفعال یا حذف نمی‌شوند. سناریوهای کنترل دسترسی، جعل callback،
لغو مجوز قبل از تأیید، race حذف هم‌زمان مدیران، Rollback و ثبت یک‌باره مدیر
بدون نیاز به چند حساب واقعی پوشش داده می‌شوند.

## محدوده و سیاست امنیتی

هنوز بازخورد پذیرفته نمی‌شود. بررسی دسترسی به محتوای بازخورد در سرویس‌های مراحل
۴ و ۵ روی همین مدل مجوز بنا می‌شود. این مرحله فقط مدیریت هویت و نقش‌ها را فعال می‌کند.
فهرست کاربران و شناسه تلگرام آنها فقط برای مدیر دارای manage_users قابل مشاهده
است؛ این فهرست هیچ ارتباطی با پیام‌ها یا نویسنده پیام ندارد.

تغییر وضعیت/نام حسابی که سابقه مدیریت دارد، علاوه بر manage_users به manage_admins
نیاز دارد؛ این کار مانع دورزدن محدودیت مدیر داخلی با غیرفعال‌کردن مدیر دیگر می‌شود.
مدیر حوزه‌ای اختیار سراسری مدیریت مدیران دریافت نمی‌کند.

فرم‌های مدیریت موقتاً در حافظه، با انقضای ۱۰ دقیقه‌اند و بعد از Restart حذف
می‌شوند. اطلاعات نهایی در دیتابیس پایدار است. این فرم‌ها برای محتوای بازخورد
استفاده نمی‌شوند؛ state رمزگذاری‌شده آن در مرحله ۴ پیاده‌سازی می‌شود.
