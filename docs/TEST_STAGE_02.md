# تست مرحله دوم: دیتابیس و رمزگذاری

این مرحله زیرساخت داده را فراهم می‌کند؛ مدیریت کاربران و مجوزهای دیتابیسی در
مرحله ۳ و ارسال واقعی بازخورد در مرحله ۴ اضافه می‌شوند. ربات همچنان فقط وضعیت
و راهنما را به حساب‌های اولیه نمایش می‌دهد.

## نتیجه بررسی توسعه‌دهنده

- ۷۱ تست خودکار پاس شد؛ شامل اجرای CLI در فرایند مستقل و حالت encoding ویندوز.
- Ruff و بررسی قالب هر ۳۰ فایل Python پاس شدند.
- keys-init در پروژه اجرا شد؛ شش کلید مستقل، بدون نمایش مقادیر ساخته شدند.
- db-upgrade واقعی و اجرای مجدد آن موفق بودند؛ نسخه هر سه دیتابیس 0001 است.
- db-check واقعی هر سه دیتابیس را OK اعلام کرد.
- `.env` موجود تغییر نکرد؛ اتصال Telegram پس از Restart را کاربر بررسی می‌کند.
- مرحله ۳ هنوز آغاز نشده است.

## تست خودکار، بدون شبکه و بدون داده واقعی

در PowerShell پوشه پروژه:

```powershell
uv sync --locked
uv run --locked pytest -q
uv run --locked ruff check .
uv run --locked ruff format --check .
```

تست‌ها در پوشه‌های موقت با کلیدهای تصادفی مستقل اجرا می‌شوند؛ `.env`، کلید و
دیتابیس واقعی شما دستکاری نمی‌شوند. سناریوهای خرابی و حذف فایل فقط روی همین
داده آزمایشی انجام می‌شوند؛ آنها را دستی روی داده واقعی تکرار نکنید.

## راه‌اندازی محلی

اگر ربات مرحله اول هنوز در ترمینال باز است، با Ctrl+C متوقفش کنید. `.env`
قبلی معتبر است؛ نیازی به تغییر توکن یا شناسه مدیر نیست. مسیر پیش‌فرض دیتابیس
`data` و مسیر جداگانه کلید `.secrets` است. برای تغییر مسیر کلید می‌توان
`SECRETS_DIR` را به `.env` اضافه کرد. دو پوشه نباید داخل یکدیگر باشند.

اگر کلید و دیتابیس قبلاً توسط توسعه‌دهنده آماده شده‌اند، مستقیم `db-check`
را اجرا کنید. در نصب تازه:

```powershell
uv run --locked python -m app.cli keys-init
uv run --locked python -m app.cli db-upgrade
uv run --locked python -m app.cli db-check
```

انتظار از db-check:

```text
identity: OK | internal: OK | external: OK | schema: 0001
```

سه فایل `identity.db`، `internal.db` و `external.db` در پوشه داده ساخته می‌شوند؛
فایل‌های جانبی `-wal` و `-shm` هنگام اتصال طبیعی هستند. شش کلید مستقل در
`.secrets/keyring.json` نگهداری می‌شوند؛ محتویات این فایل را بازنشر نکنید.

اجرای دوباره `db-upgrade` باید موفق و بدون پاک‌شدن داده باشد. اجرای دوباره
`keys-init` باید رد شود؛ این رفتار صحیح است و کلید موجود را عوض نمی‌کند.
اگر دیتابیس وجود دارد ولی کلید گم شده، ساخت کلید جایگزین ممنوع است و باید
نسخه اصلی کلید را از محل امن بازیابی کرد.

## اجرای ربات

```powershell
uv run --locked python -m app.main
```

ربات قبل از اتصال Telegram صحت هر سه دیتابیس و تطابق کلیدها را بررسی می‌کند.
`/start` باید «مرحله ۲ از ۱۰» را نمایش دهد. دکمه‌ها همچنان کار می‌کنند و دریافت
بازخورد هنوز غیرفعال است. نمایش مرحله ۱ یعنی فرایند قبلی هنوز اجرا می‌شود.

## معیار قبولی

- همه تست‌های خودکار و بررسی کیفیت کد پاس شوند.
- db-check هر سه حوزه را OK اعلام کند.
- db-upgrade تکراری موفق باشد و keys-init تکراری، بدون بازنویسی رد شود.
- ربات بعد از Restart پیام مرحله دوم را نشان دهد.
- هیچ کلید، توکن، هویت نویسنده یا متن بازخورد در خروجی چاپ نشود.

در خطای ذخیره‌سازی، فایل‌ها را حذف نکنید. مسیرها، وجود کلید اصلی، توقف فرایند
قدیمی، دسترسی پوشه و فضای دیسک بررسی شوند. پیام خطا عمداً پارامترهای SQL یا
محتویات کلید را نشان نمی‌دهد. در Linux پوشه‌های خصوصی باید 0700 و فایل‌های
کلید/دیتابیس 0600 باشند؛ در Windows کنترل دسترسی با ACL پوشه است.
