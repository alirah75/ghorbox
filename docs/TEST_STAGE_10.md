# آزمون نهایی مرحله ۱۰

نسخه 1.0.0، Schema 0001. کلید یا دیتابیس موجود را دوباره نسازید. این مرحله
فایل‌های Docker، Compose، واحد systemd، راهنمای استقرار و آزمون چرخه اجرا را
اضافه می‌کند. نصب روی سرور یا ارسال پیام واقعی توسط توسعه‌دهنده انجام نشده است.

## نتیجه بررسی توسعه در ۲۰۲۶/۰۹/۲۲

- مجموعه ۲۱۷ تست بررسی شد: ۲۱۶ موفق در اجرای کامل؛ یک انتظار قدیمی متن مرحله ۹
  اصلاح شد و همان تست در اجرای مجدد موفق شد. خطای حل‌نشده‌ای در این مجموعه باقی نماند.
- Ruff و قالب‌بندی هر ۷۶ فایل Python موفق بود.
- db-check هر سه دیتابیس موجود با Schema 0001 موفق بود؛ داده فعال پاک‌سازی یا بازیابی نشد.
- ساخت Wheel نسخه 1.0.0 و نصب غیر editable بدون وابستگی‌های توسعه، همراه آزمون
  آفلاین CLI برای راه‌اندازی، پشتیبان، بررسی بسته و بازیابی موفق بود.
- compose.yaml و فایل setup با JSON Schema رسمی Compose اعتبارسنجی شدند.
- Docker build/run، systemd-analyze و اتصال واقعی Telegram در این مرحله اجرا نشدند.
  موارد این بخش، تأیید چک‌لیست سرور پایین صفحه نیستند.

## بررسی روی Windows فعلی

ربات قبلی را متوقف کنید و از پوشه پروژه اجرا کنید:

```powershell
uv sync --locked
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked pytest -q
uv run --locked python -m app.cli db-check
uv run --locked python -m app.main
```

پس از /start پیام نسخه ۱.۰ و مرحله ۱۰ نمایش داده شود. پشتیبان و عملیات نگهداری
مطابق [مرحله ۹](TEST_STAGE_09.md) است. خودکارسازی نگهداری همچنان پیش‌فرض خاموش است.

## پذیرش با دو حساب عضو و یک مدیر

- [ ] حساب ثبت‌نشده و حساب غیرفعال وارد امکانات اصلی نمی‌شوند.
- [ ] مدیر تا ۱۰ عضو را با یک انتخاب و تأیید گروهی اضافه می‌کند و اعضا /start می‌زنند.
- [ ] عضو اول برای عضو دوم متن داخلی می‌فرستد؛ پیش‌نمایش و تأیید درست‌اند.
- [ ] عضو دوم متن را بدون نام، شناسه یا Forward نویسنده دریافت می‌کند.
- [ ] پاسخ به تاریخچه درست برمی‌گردد و حساب سوم به آن گفتگو دسترسی ندارد.
- [ ] فرم لغوشده یا دکمه دوباره‌زده‌شده پیام تکراری ایجاد نمی‌کند.
- [ ] فرد خارجی انتخاب/پیشنهاد می‌شود؛ صندوق و پاسخ واسطه خارجی مستقل‌اند.
- [ ] مدیر صرفاً خارجی به پنل مدیریتی داخلی، پیام‌ها و آمار داخلی دسترسی ندارد.
- [ ] مدیر داخلی فقط بازخورد اولیه گیرندگان گروه خودش را می‌بیند؛ مدیر اصلی همه گروه‌ها را می‌بیند.
- [ ] هیچ دکمه یا مسیر فعالی برای گزارش پیام یا بستن دستی گفتگو وجود ندارد.
- [ ] آمار گروه کوچک پنهان است؛ گزارش فقط به مدیر دارای مجوز همان حوزه می‌رسد.
- [ ] با توقف و شروع دوباره، تاریخچه باقی می‌ماند؛ فرم مدیریت در صورت لزوم دوباره آغاز می‌شود.
- [ ] backup-check و restore در پوشه آزمایشی جدید موفق‌اند؛ مسیر فعال خودکار عوض نمی‌شود.

پاسخ گیرنده برای نویسنده اولیه می‌تواند قابل انتساب باشد، چون خود او گیرنده
را انتخاب کرده است. ناشناس‌بودن اولیه، شناسایی از روی متن یا دسترسی ریشه سرور
را پوشش نمی‌دهد؛ [مرزهای امنیت](ARCHITECTURE.md) را پیش از استفاده واقعی بخوانید.

## پذیرش استقرار روی سرور آزمایشی

فقط یکی از مسیرهای [راهنمای استقرار](DEPLOYMENT.md) را دنبال کنید. Docker و
systemd در محیط Windows توسعه قابل اجرا نبودند؛ این موارد هنوز نیازمند تست سرورند:

- [ ] Docker: build، compose config و آزمون offline تصویر موفق شوند.
- [ ] یا systemd: systemd-analyze verify، db-check و شروع سرویس موفق شوند.
- [ ] فایل کلید فقط برای حساب اجرا قابل خواندن و مسیرها مستقل باشند.
- [ ] ربات بعد از شروع سرویس با حساب آزمایشی پاسخ دهد.
- [ ] stop در مهلت ۶۰ ثانیه تمام شود و start مجدد قفل باقی‌مانده نداشته باشد.
- [ ] پس از Restart میزبان، تنها یک نمونه بالا بیاید و تاریخچه باقی بماند.
- [ ] پس از قطع موقت شبکه و برگشت اتصال، ارسال جدید موفق شود؛ uncertain خودکار تکرار نشود.
- [ ] نسخه کد قبلی و backup بررسی‌شده برای بازگشت در دسترس باشند.
- [ ] فضای دیسک، سلامت سرویس و برنامه پشتیبان‌گیری مسئول مشخص داشته باشند.

فایل `.github/workflows/verify.yml` آزمون Windows/Linux و ساخت/آزمون آفلاین
کانتینر را برای مخزن GitHub آماده می‌کند. این workflow اینجا اجرا یا منتشر نشده است.
پذیرش نهایی پس از موفقیت این چک‌لیست توسط شما ثبت می‌شود.
