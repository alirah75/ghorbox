# تست مرحله ۹: پشتیبان، بازیابی و نگهداری

نسخه 0.9.0 است. Schema همان 0001 است؛ کلید و دیتابیس موجود را دوباره نسازید.
صحت‌سنجی توسعه: هر ۲۱۰ تست پروژه موفق شد؛ بررسی کد و قالب‌بندی نیز موفق بود.
db-check روی هر سه دیتابیس فعلی موفق شد. پاک‌سازی یا بازیابی روی داده فعال اجرا نشده است.
دستورهای این راهنما در پوشه پروژه اجرا می‌شوند. برای عملیات آفلاین، ابتدا
اجرای ربات را متوقف کنید. یک قفل سیستم‌عامل از اجرای دو نسخه روی یک پوشه داده
جلوگیری می‌کند و پس از بسته‌شدن یا قطع فرایند خودکار آزاد می‌شود؛ فایل قفل را حذف نکنید.

```powershell
uv sync --locked
uv run --locked python -m app.cli db-check
```

## ۱. ساخت و بررسی نسخه پشتیبان

یک نام جدید انتخاب کنید؛ فایل موجود بازنویسی نمی‌شود:

```powershell
uv run --locked python -m app.cli backup --output backups/stage09-first.afb
uv run --locked python -m app.cli backup-check --source backups/stage09-first.afb
```

پشتیبان شامل هر سه دیتابیس است؛ `.env`، توکن، فایل کلید و Log داخل آن نیستند.
کل بسته، از جمله اطلاعات هویت، رمزگذاری و اعتبارسنجی می‌شود. کلید رمزگذاری
بسته با HKDF و salt مستقل از کلید موجود مشتق می‌شود. کلید اصلی را **جداگانه**
در محل امن نگه دارید؛ فایل `.afb` بدون کلید اصلی قابل بازیابی نیست. از دست‌رفتن
یا ساخت مجدد کلید را با ابزار backup نمی‌توان جبران کرد.

Snapshot با SQLite Backup API و قفل نوشتن هر سه دیتابیس تهیه می‌شود؛ کپی ساده
فایل `.db` در حضور WAL انجام نمی‌شود. اصالت بسته، هش فایل‌ها، ساختار دیتابیس،
تطابق کلید و رمزگشایی فیلدهای رمزگذاری‌شده بررسی می‌شوند. backup-check فقط در
پوشه موقت بررسی می‌کند و داده فعال را جایگزین نمی‌کند.

پوشه‌های موقت ممکن است هنگام عملیات حاوی اطلاعات هویت رمزگشایی‌شده باشند و
در پایان عادی یا خطای قابل‌مدیریت پاک می‌شوند. در قطع برق یا پایان اجباری
فرایند ممکن است باقی بمانند؛ پوشه‌های `.backup-*` و `.restore-*` را خصوصی نگه
دارید. در Windows دسترسی پوشه از ACL والد به ارث می‌رسد. روی دیسک مشترک عمومی
این عملیات را اجرا نکنید. فایل خروجی نیمه‌کاره ناشی از قطع عملیات معتبر نیست؛
با backup-check بررسی کنید و برای تلاش بعد نام جدید بگذارید.

## ۲. بازیابی آزمایشی، بدون دست‌زدن به داده فعال

پوشه هدف نباید از قبل وجود داشته باشد:

```powershell
uv run --locked python -m app.cli restore --source backups/stage09-first.afb --target recovery/stage09-first
```

این دستور `DATA_DIR` را تغییر نمی‌دهد و هیچ فایل موجودی را بازنویسی نمی‌کند.
در تست اولیه همین کافی است؛ ربات اصلی را همچنان از مسیر قبلی اجرا کنید.
برای بازیابی واقعی، پس از بررسی نتیجه و توقف ربات قبلی، DATA_DIR در `.env`
را به پوشه بازیابی‌شده تغییر دهید، SECRETS_DIR را روی کلید اصلی نگه دارید و
db-check بگیرید. سپس فقط یک نمونه ربات را اجرا کنید. اجرای هم‌زمان دو پوشه با
یک توکن تلگرام مجاز نیست؛ قفل برنامه فقط استفاده هم‌زمان از **یک پوشه** را مهار می‌کند.

اگر بازیابی وسط کار قطع شود، پوشه هدف با `.restore-incomplete` علامت‌گذاری
می‌شود و برنامه آن را باز نمی‌کند. علامت را دستی حذف نکنید؛ فایل اصلی backup
را بررسی و بازیابی را در **پوشه جدید دیگری** انجام دهید. مسیر داده قبلی محفوظ است.

پس از بازیابی:

- هویت، عضویت، گفتگو و تاریخچه تا زمان Snapshot برمی‌گردند؛ داده پس از آن
  زمان در نسخه پشتیبان وجود ندارد.
- فرم‌ها و دکمه‌های ذخیره‌شده قدیمی پاک می‌شوند؛ از `/start` آغاز کنید.
- صف‌های قبلی pending/sending به uncertain تبدیل می‌شوند و خودکار دوباره
  ارسال نمی‌شوند؛ شاید پیام پس از زمان پشتیبان قبلاً در تلگرام تحویل شده باشد.
- برای جلوگیری از تولید دوباره گزارش‌های هفتگی ازدست‌رفته پس از Snapshot،
  بازه‌های تا آخرین موعد انتشار گذشته در زمان بازیابی دوباره تولید/ارسال
  نمی‌شوند. آرشیو موجود در Snapshot باقی می‌ماند؛ از موعد هفتگی بعد ادامه می‌یابد.
  این مرز در `.recovery.json` است؛ آن را حذف یا تغییر ندهید.
- آمار دوره بعد بر پایه داده بازیابی‌شده و داده جدید است و ممکن است داده‌های
  پس از زمان Snapshot که از دست رفته‌اند را نداشته باشد.

## ۳. پیش‌نمایش نگهداری؛ بدون حذف

```powershell
uv run --locked python -m app.cli maintenance
```

خروجی برای هر حوزه تعداد گفتگوهای قابل انقضا/حذف، فرم‌های منقضی و تحویل‌های
مبهم را نشان می‌دهد. پیش‌نمایش هیچ رکوردی را حذف نمی‌کند. پس از بررسی خروجی
و تهیه پشتیبان معتبر، اجرای واقعی با دستور جداگانه انجام می‌شود:

```powershell
uv run --locked python -m app.cli maintenance --apply
```

سیاست این مرحله:

- گفتگوهای باز پس از رسیدن به انقضای ۹۰روزه از آخرین پاسخ پذیرفته‌شده، expired
  می‌شوند. بدون پاک‌سازی هم سرویس پاسخ، انقضای زمانی را کنترل می‌کند.
- گفتگو با حداقل **۱۸۰ روز از آخرین فعالیت ثبت‌شده**، اگر گزارش باز ندارد،
  همراه پیام‌ها، گزارش‌های بررسی‌شده، دسترسی‌ها و صف متعلق به همان پیام‌ها
  حذف می‌شود. این مهلت از آخرین فعالیت/تغییر گفتگو است، نه عمر تک‌تک پیام‌ها؛
  گفتگوی فعال می‌تواند پیام‌های قدیمی‌تر از ۱۸۰ روز داشته باشد.
- گزارش باز، حذف محتوای مربوط را تا بررسی مدیر به تعویق می‌اندازد. بستن یا
  رسیدگی مدیریتی ممکن است زمان آخرین فعالیت را به‌روز کند.
- هر اجرا در هر حوزه حداکثر ۱۰۰ گفتگو و ۱۰۰ پیشنهاد خارجیِ بررسی‌شده قدیمی
  را حذف می‌کند. برای داده زیاد، اجراهای بعدی ادامه می‌دهند.
- فرم‌های منقضی پاک می‌شوند. شناسه‌های مشارکت هفتگی بسیار قدیمی پاک می‌شوند؛
  گزارش‌های هفتگی منتشرشده و صف آنها برای حفظ نسخه ثابت و جلوگیری از تکرار باقی می‌مانند.
- داده‌های هویت، کاربران، مدیران و سابقه مدیریت حذف نمی‌شوند. پیشنهاد خارجی
  در انتظار بررسی هم نگه داشته می‌شود.
- صف pending مربوط به گفتگوی بسته/منقضی/معلق متوقف می‌شود. ارسال sending که
  مهلت آن گذشته، uncertain می‌شود و کورکورانه تکرار نمی‌شود.

هر حوزه تراکنش مستقل دارد؛ خطا تغییرات نیمه‌کاره همان حوزه را برمی‌گرداند.
بین دو فایل، تراکنش مشترک وجود ندارد؛ تکرار عملیات ادامه امن آن را انجام می‌دهد.
آمار شخصی و تاریخچه، پس از حذف گفتگو، فقط داده باقی‌مانده را نمایش می‌دهند؛
آمار هفتگی قبلاً منتشرشده ثابت می‌ماند.

پاک‌سازی، پیام ارسال‌شده به تلگرام یا نسخه‌های پشتیبان قدیمی را حذف نمی‌کند.
secure_delete فعال است، اما حذف فیزیکی تضمین‌شده از SSD، WAL، Snapshot سیستم‌عامل
یا Backup ارائه نمی‌شود. نگهداری و حذف فایل‌های backup مسئولیت بهره‌بردار است؛
این نسخه پشتیبان‌های قدیمی را خودکار حذف نمی‌کند و رمز کلید را نیز تعویض نمی‌کند.

## ۴. فعال‌کردن اجرای دوره‌ای

پیش‌فرض خاموش است. فقط بعد از بررسی پیش‌نمایش و آماده‌بودن پشتیبان، این خط را
در `.env` تنظیم و ربات را دوباره اجرا کنید:

```dotenv
RETENTION_ENABLED=true
```

در این حالت نگهداری در شروع برنامه و سپس هر ساعت اجرا می‌شود. برای خاموش‌کردن
آن false بگذارید و ربات را دوباره اجرا کنید. پشتیبان‌گیری خودکار زمان‌بندی‌شده
در این مرحله اضافه نشده؛ دستور backup را طبق برنامه عملیاتی خود اجرا کنید.

## ۵. تست خرابی بدون دست‌زدن به داده واقعی

```powershell
uv run --locked pytest tests/test_maintenance_backup.py -q
```

این تست‌ها فقط فایل موقت دارند: پشتیبان/بازیابی، کلید اشتباه، خرابی بسته و متن
رمزگذاری‌شده، فایل مسیر نامعتبر، مقصد موجود، قفل اجرا، قطع بازیابی، پیش‌نمایش،
حذف تراکنشی، حفظ گزارش باز و جلوگیری از ارسال دوباره. تغییر دستی فایل‌های واقعی
یا ساعت سیستم برای تست لازم نیست.

برای استفاده از قابلیت‌های ربات، اجرای معمول و `/start`:

```powershell
uv run --locked python -m app.main
```

Docker، systemd و جمع‌بندی استقرار، مرحله ۱۰ هستند. نسخه فعلی هنوز تحویل نهایی
Production نیست.
